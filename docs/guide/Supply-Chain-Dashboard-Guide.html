1. What the project does

The dashboard turns one sales-and-inventory CSV into answers to three questions: what is selling, where stock will run out, and what happens if the supply chain is disrupted.

You load a CSV. The backend cleans it with pandas and computes every metric. The browser draws those metrics as charts. Groq, a hosted large language model, then explains the numbers in plain English. The model never invents the numbers: it only receives ones the backend already computed.

Each CSV row is one sale record. Six columns are required: date, units_sold, price_unit, delivery_days, delivered_qty, stock_available. Optional columns (region, channel, category, sku, promotion_flag) unlock the breakdowns.

ViewQuestion it answersWhat you see
OverviewHow healthy is the business right now?Five KPI cards with deltas and sparklines, revenue trajectory vs moving average, proactive signals, top stock deficits, recommended actions
Demand & SalesWhere does revenue come from, and does price move volume?Region × channel stacked revenue, channel efficiency matrix, price-elasticity scatter with fitted curve, category bars
OperationsAre deliveries late, and which items are short?Lead-time histogram with normal curve, lead time by region, stock vs velocity quadrant, replenishment queue
SeasonalityWhen and where does demand peak, and what comes next?Season × region heatmap, 7-period forecast with 95% band, seasonal volume and lead time
Scenario LabWhat if suppliers slip or demand surges?Sliders with live lost sales, stockout probability, fill rate, holding cost, delay curve
Intelligence HubWhat should I do about it?AI insight pills, one-click prompts, demand split, recommendations

Two features run across every view. The Copilot (⌘K or Ctrl+K, or the floating pill) is a chat drawer. The Inspect button on every chart sends that chart's data to the copilot with a tailored question. Four filters (region, channel, category, season) apply to every view and to everything the AI sees.

2. Architecture map

Blue boxes are the two files to understand first: services/api.js is the browser's only door to the server, and DataService is where every number starts.

Reading the map, box by box

PartWhat happens there
BrowserReact draws everything. App.jsx holds the filters and the active view; the views are plain functions of one data object. No business logic lives here: the browser formats and draws.
api.jsEvery request leaves through this file. It uses axios for normal JSON calls and a small hand-written reader for the copilot's streamed answers.
app.pyStarts the server, loads backend/.env (where your Groq key lives), allows the browser's origin (CORS), handles uploads, and can preload a dataset at start-up.
routes/Thin HTTP layer. Each function reads query parameters or a JSON body, calls a service, and turns Python errors into HTTP errors. analytics.py serves the dashboard; ai.py serves the copilot, insights and scenarios.
DataServiceOwns the dataset: cleaning, filtering, every aggregation and the cache. Everything else asks it for data.
InsightEngineTurns DataService output into words: the dense data brief sent to Groq, the rule-based insight scan, and the offline answers used when Groq is unavailable.
simulation.pyThe what-if inventory model behind the Scenario Lab. Pure maths, no AI.
GroqServiceThe only file that talks to Groq: builds the prompt, streams the answer, retries on a retired model, and falls back to InsightEngine on any error.
OutsideThe CSV files on disk, the Groq API on the internet, and the secret key in backend/.env, which git ignores.
The one idea to rememberThe backend is the single source of truth. The browser never computes a metric, and Groq never computes a number. That is why the dashboard still works with no key: only the wording changes.

4. Flow: from CSV to dashboard

Steps 1 to 4 run once per upload; steps 5 and 6 run on every filter change.
Read top to bottom. Solid arrows are requests, dashed arrows are responses.

What each step does, in code

  1. Upload. POST /upload saves the file under backend/uploads/. The filename is reduced to its last part, so a name like ../../app.py cannot escape the folder.
  2. Validate. process_upload() rejects the file with a 400 listing any missing required column.
  3. Clean and enrich. _preprocess() converts types, drops rows with missing values or non-positive price, and adds: season (from the month), revenue = units × price, on_time (≤ 3 days), in_full (delivered ≥ sold), and segment (SKU · region).
  4. Hold in memory. The DataFrame lives on the single data_service object. There is no database: a restart forgets it unless DEFAULT_DATASET is set.
  5. Filter. filtered() builds a True/False mask from the query string. channel=Retail,Discount selects both.
  6. Aggregate and cache. _build_payload() runs about 20 small functions and stores the result under a key made from the filters, so revisiting a filter is instant. A new upload clears the cache.
Why one big payload?One request gives every view what it needs, so switching views is instant and all charts always agree with each other. Only the copilot, the insight scan and the Scenario Lab make their own requests, because they are slower or interactive.

5. Flow: asking the copilot

The red dashed step is the fallback path: if Groq fails at any point, the local engine streams an answer through the same pipe.

Context hydration: what Groq actually receives

The model never sees your CSV. _messages() sends four things:

  1. Persona: "You are an elite Chief Supply Chain Officer and Quantitative Operations Analyst…", which keeps answers numeric and concrete.
  2. Answer format: four required sections (Executive answer, Root cause hypothesis, Tactical actions with dollar impact, Metric citations) and a glossary of velocity, cover and reorder point.
  3. Data brief from build_context(): about 15 dense lines with dataset, rows, date range and filters; KPIs; lead time by region, channel and season; the 5 tightest SKU-locations; the seasonality index grid; revenue by channel, region and category; elasticity; quadrant counts; the forecast. For an Inspect click, up to 40 rows of that chart are appended.
  4. History: the last 8 exchanges, so follow-ups like "and in the South?" work.

Streaming, step by step

The route returns text/event-stream. Each event is one line, data: {json}, followed by a blank line. The first event, meta, says who is answering; many delta events carry text; done ends it. In the browser, streamAIQuery() reads the response body chunk by chunk, splits on blank lines, and calls back for each event. The drawer appends the text, which gives the typewriter effect.

Every path ends in an answer. The note at the top of a fallback answer quotes Groq's exact error, for example an expired key.

6. Flow: proactive insights

Proactive insights run the opposite way to the copilot: Python rules find the problems, and Groq only rewrites the wording. InsightEngine.proactive_insights() checks, on the filtered data:

CheckRuleSeverity
Stockout hazardAny SKU-location below its 95% reorder point, or whose cover is shorter than lead time + 7 daysCRITICAL / WARNING
Lead-time anomalyDeliveries slower than mean + 2σCRITICAL if over 3% of orders
SLA breachMore than 20% of deliveries beyond the 3-day SLAWARNING
Margin leakPromoted orders earn less revenue per order than unpromoted onesWARNING
Seasonal mismatchThe peak-demand season carries less stock per unit sold than averageWARNING / OPPORTUNITY
Channel gapBest region × channel earns over 3% more per unit than the worstOPPORTUNITY
Revenue momentumLatest 28 days moved 5% or more vs the 28 beforeWARNING / OPPORTUNITY

Hits are sorted by severity, then by estimated dollar impact, and the top 6 are kept. With a key set, GroqService.proactive_insights() asks Groq, in JSON mode, to tighten each title, detail and action while keeping ids, severities and numbers. If that call fails, the rule text is shown unchanged.

On fmcg_clean.csv the scan returns four pills: SLA breach rate 40.2% (PL-South slowest), 47 segments with thin cover, Monsoon under-stocked for its demand (7.07 units of stock per unit sold vs 8.0 average), and promotions that lift units 95%.

7. Flow: the Scenario Lab

The figures come only from the maths below; Groq is involved only if you press Generate briefing.

The model, in five steps

  1. Shift the inputs for every SKU-location: lead time L → (L + delay) × (1 + spike%); demand d → d × (1 + surge%) × (1 + price change)elasticity; stock S → S × buffer.
  2. Lead-time demand is treated as a normal distribution with mean μ = d·L and spread σ = √(L·σd² + d²·σL²). Both day-to-day demand and the lead time itself vary.
  3. Stockout probability is the chance demand exceeds stock: P = 1 − Φ(z), with z = (S − μ) / σ.
  4. Units short per cycle use the standard normal loss function below. Multiplying by 30 / L cycles gives lost units over 30 days; × price gives lost sales.
  5. Holding cost = stock value × 25% a year × 30/365, so you can see what a bigger buffer costs.
E[short] = σ · ( φ(z) − z · (1 − Φ(z)) )

On fmcg_clean.csv, adding 8 days of supplier delay moves 30-day lost sales from $119 to $101.5K and fill rate from 100% to 82.5%. The delay curve shows that losses stay near zero for a few days and then climb steeply, which is the shape you would expect when stock covers about 8 days of demand.

8. The analytics, explained

Most numbers come from one idea: treat each segment (one SKU in one region) as a small warehouse, and compare how many days its stock lasts with how long a refill takes.

Assumptions you can changeFour constants at the top of data_service.py set the business rules: OTIF_SLA_DAYS = 3, REVIEW_PERIOD_DAYS = 7, SERVICE_Z = 1.65 (95% service level) and VELOCITY_WINDOW_DAYS = 7. OTIF is 59.8% only because 40% of FMCG deliveries take 4 or 5 days against the 3-day SLA.

Two details prevent misleading charts. Weekly series drop a final partial week, which otherwise looks like a demand collapse. The fitted elasticity is clamped between −3 and −0.1 inside the simulator so a noisy fit cannot produce absurd demand swings.

9. Frontend internals

How state flows

App owns the filters. It passes them to useDashboardData, which fetches the payload, and to CopilotProvider, so every AI request carries the current filters. Views receive data as a prop and render; they hold almost no state of their own.

PieceJobDetail worth knowing
useDashboardDataFetch, refetch on filter change, upload, load sampleNumbers each request and ignores stale replies, so fast filter clicks never show old data. Skeletons appear only on the first load.
CopilotContext + CopilotChatContextCopilot actions vs chat transcriptSplit so streamed tokens re-render only the drawer, not the dashboard.
SectionCardEvery card; owns the Inspect buttoninspect={{ data, query }} is all a chart needs to get AI help.
useMountAnimationCharts animate onceLater updates swap in place instead of replaying the draw-in.
useCountUpKPI numbers glide to new valuesEase-out over 0.9 s; disabled when the OS asks for reduced motion.
ErrorBoundaryContains crashesA broken view shows an error card with Try again instead of a blank page.
MarkdownRenders copilot answersDependency-free: headings, lists, tables, code, quotes, bold.

The design system

All styling flows from CSS variables in styles/tokens.css. Surfaces are obsidian (#0B0F17, #111827, #161F30) with 8%-white hairline borders. Four status colours carry meaning: emerald #10B981 healthy, amber #F59E0B warning, coral #EF4444 critical, ice blue #38BDF8 primary. Text uses Inter with −0.015em tracking; every number uses JetBrains Mono with tabular figures so digits line up in columns. One spring curve (--ease-spring) drives hover lifts, view transitions and the drawer. Charts read the same palette from utils/chartTheme.js, and tooltips use a 12px backdrop blur.

Views live in the URL hash (/#operations), so a link opens the right view, and keys 1 to 6 switch between them.

10. Lessons from the bugs we fixed

Four problems came up after the first build. Each one teaches something general, so they are worth understanding.

SymptomCauseFixLesson
"Connect Groq" stayed on after adding the keyThe key was pasted into backend/.env.example; the app reads backend/.envMoved the key to .env (git-ignored), restored the template.example files are committed templates. Secrets go only in ignored files.
"Groq was unreachable (NotFoundError)"Groq retired llama-3.3-70b-versatile for this keyDefault openai/gpt-oss-120b; auto-retry on an available model; exact error shownHosted model names change. Ask the API what exists, and surface real error messages.
Page flickered, content vanishedEvery streamed token re-rendered the whole app; Recharts replayed its draw-in on each new data arraySplit the copilot context; animate charts on first mount onlyIn React, put fast-changing state where only its consumers subscribe.
"minimumFractionDigits is out of range"The tooltip called formatNumber(value, row), so the data row became the decimal countOne-argument default formatter; every formatter clamps digits to 0–20Be careful passing a two-argument function as a callback; validate inputs at the edge.

The flicker fix was measured: while a 2,412-character answer streamed in, chart elements changed 0 times. The tooltip fix was tested by hovering every chart on all six views: 78 tooltips, 0 errors, against 8 errors out of 8 hovers before.

13. Extend it, and a learning path

Every feature follows one route: compute it in a backend service, expose it in the payload or a route, then draw it in a page.

Add a KPI card

  1. In data_service.py, add a dict to the list in _kpis(): key, label, format (currency, percent, turns, index, days), value, delta, status, sparkline.
  2. That's all: KPIGrid renders every item. Adjust .grid--kpi for six columns.

Add a chart

  1. Write _my_series(df) and add it to _build_payload().
  2. In a page: <SectionCard title="…" inspect={{ data: data.my_series }}> around a Recharts chart, using axisProps, gridProps, COLORS and <ChartTooltip rows={…}/>.
  3. Add isAnimationActive={animate} from useMountAnimation() to each series.

Add an AI feature

  1. Add a method on GroqService that builds messages with _messages() and calls self._create(…); the model fallback comes free.
  2. Add a rule-based fallback in InsightEngine so it works without a key.
  3. Expose it in routes/ai.py and call it from api.js.

Suggested reading order

  1. data_service.py: _preprocess, segment_table, _kpis
  2. insight_engine.py: build_context, proactive_insights
  3. groq_service.py: _messages, _create, stream_query
  4. api.js + CopilotContext.jsx: streaming to screen
  5. OperationsPage.jsx: a full view using every building block
